# План фичи: симуляция собеседования (Job Interview Simulation)

## 1. Цель и суть фичи

Кандидат проходит симуляцию технического собеседования на позицию, связанную с SQL
(SQL Developer, Data Engineer, DBA и т.д.), на выбранный им грейд (junior/middle/senior).
Взаимодействие имитирует реальное интервью: вымышленная компания рассказывает о себе и
о вакансии, кандидат представляется, дальше идёт смешанный блок вопросов (теория +
практические SQL-задачи), а в конце — итоговый отчёт с процентом успеха, сильными и
слабыми сторонами и рекомендациями, что подтянуть.

**Доступ и модель монетизации**: страница компании с описанием вакансий и выбором
позиции/грейда (`interview-start`) **открыта для всех** — в том числе неавторизованных
посетителей, без пейволла и без редиректа на логин. Вход и оплата проверяются только
**после** того, как кандидат уже выбрал конкретную пару позиция/грейд — то есть в момент
нажатия "Start Interview" (см. флоу, шаг 2, и п. 3.2.2). Сама симуляция интервью (после
этого клика) доступна только зарегистрированным пользователям и является платной —
это осознанно снимает ограничение на бюджет LLM — в отличие от бесплатного
`checkFreeAnswer`, здесь LLM может комментировать **каждый** неверный ответ (а не только
вопросы типа `free_answer`), что и делает симуляцию похожей на живое интервью, а не на
автотест с чекмарками (см. п. 4.3).

Пользовательский флоу:

1. **Знакомство с компанией и выбор позиции/грейда — доступно всем, без входа**:
   страница `interview-start` открывается для любого посетителя, авторизован он
   или нет. Проверка активной (незавершённой) сессии интервью выполняется
   только для уже залогиненных пользователей — если она есть, вместо выбора
   позиции/грейда показывается текст-приглашение и кнопка "Продолжить
   интервью", ведущая в уже начатую сессию. Для неавторизованных посетителей
   активной сессии по определению нет, и сразу показывается экран из п. 2.
2. ✅ **Выбор параметров + знакомство с компанией — один экран, сделано**
   (п. 3.1.3): вымышленная компания (Meridian Logistics) рассказывает о себе,
   показывает открытые позиции (SQL Developer, Data Analyst — для MVP, п. 3.1.1)
   с описанием и грейды (junior/middle/senior) с требованиями; кандидат
   выбирает конкретную пару позиция+грейд кнопкой "Start Interview" у нужного
   грейда, без отдельного шага "сначала выберите должность вслепую". **Именно
   в момент нажатия "Start Interview"** — не раньше, когда пара позиция/грейд
   уже известна — проверяются: (а) вход в систему (не авторизован → редирект
   на логин с возвратом на выбранную пару позиция/грейд после успешного входа
   или регистрации), (б) оплата (право доступа, п. 3.5) и (в) кулдаун
   повторной попытки для этой конкретной пары (п. 4.4); любой отказ показывает
   сообщение/пейволл/логин и не создаёт сессию.
3. **Самопрезентация кандидата**: кандидат пишет о себе свободным текстом. Текст
   анализируется LLM (опыт, сильные темы, слабые места, тон, **соответствие
   выбранной позиции/грейду**) — результат влияет на подбор вопросов. Если
   соответствие неочевидно, LLM может сгенерировать один уточняющий вопрос
   кандидату; ответ на него тоже сохраняется в сессии и учитывается в финальном
   отчёте (подробности — п. 4.5). Несоответствие самопрезентации выбранному
   уровню **никогда не блокирует** прохождение — интервью продолжается в любом
   случае, максимум — щадящая корректировка сложности (п. 4.1) и
   доброжелательная рекомендация в финальном отчёте.
4. **Интервью**: последовательность теоретических и практических вопросов
   (используются существующие типы `query` / `answer` / `free_answer`). На каждый
   неверный ответ LLM даёт комментарий-подсказку; если ответ близок к правильному —
   даётся ещё одна попытка на тот же вопрос, если далёк — короткий комментарий и
   переход дальше (подробности — п. 4.3). Набор вопросов адаптируется по ходу
   (сложность/темы, п. 4.1).
5. **Итог**: процент успеха, разбивка по темам (сильные/слабые стороны),
   рекомендации (какие темы/уроки подтянуть), с сохранением полной "стенограммы"
   интервью (вопрос → ответ → комментарий интервьюера). Результат остаётся
   доступен и позже — **все попытки интервью видны в профиле пользователя**,
   каждая со своими вопросами/ответами, итогом и рекомендациями (п. 3.8), не
   только сразу после прохождения.
6. **Повторная попытка**: разрешена не раньше следующего календарного дня после
   предыдущей сессии на ту же пару позиция/грейд, набор вопросов не повторяет предыдущий
   (п. 4.4).

## 2. Что уже есть в проекте и можно переиспользовать напрямую

Ниже — конкретные существующие механизмы, на которые фича должна опираться, а не
дублировать.

### 2.1. Банк вопросов и типы проверки — переиспользуем как есть
- Таблицы `questions` / `questions_localization` (`sql/schema.sql`), поле
  `question_type` (`query` / `answer` / `free_answer`), поле `rate` (1–5, уже
  трактуется как сложность).
- `categories` / `question_categories` — тематические теги вопросов (join'ы,
  подзапросы и т.д.) — это и есть механизм "тем" для отчёта по сильным/слабым
  сторонам.
- `question_rates` / `question_rates_localization` — готовые лейблы сложности.
- Проверка ответов — **готова, ничего не дублируем**:
  - `Question::checkQueryResult()` / `Question::checkQuery()` (`lib/Question.php`) —
    практические SQL-задачи.
  - `Question::checkAnswers()` — тестовые вопросы с выбором ответа.
  - `Question::checkFreeAnswer()` — уже подключённая LLM-проверка открытых
    вопросов (`lib/LLM.php::askJson()`, профиль из `USER_ANSWER_LLM_PROFILE`).

### 2.2. Механизм "тестовой сессии" — берём за основу, не изобретаем новый
- `tests` (id, user_id, questionnire_id, grade, closed_at) +
  `test_questions` (test_id, question_id, attempts, max_attempts, solved_at,
  last_answer, query_cost) — уже описывают именно то, что нужно интервью-сессии:
  многошаговый прогресс по набору вопросов с состоянием.
- `Test::create()`, `Test::load()`, `Test::getFirstUnsolvedQuestionId()`,
  `Test::getQuestionAttemptStatus()`, `Test::saveQuestionAttempt()`,
  `Test::calculateResult()`, `Test::saveGrade()` (`lib/Test.php`) — вся оркестрация
  прохождения теста уже реализована и её можно специализировать по аналогии
  с MariaDB Challenge (см. ниже).

### 2.3. Готовый архитектурный прецедент — "кастомный брендированный тест"
`Test::challenge_mariadb_create()` + `Controller::challenge_mariadb*()` +
`templates/{lang}/challenge-mariadb.tpl` + `mariadb_challenge_result.tpl` — это
**почти точная модель** того, что нужно для интервью-симуляции: фиксированный
(или сгенерированный) набор вопросов, своя посадочная страница, свой расчёт
результата, свой шаблон результата. Новую фичу стоит делать по этому же
паттерну (свой `questionnire`, свои методы в `Test`, свои экшены в `Controller`,
свои роуты в `Router.php`).

### 2.4. LLM-инфраструктура — переиспользуем сам механизм, пишем новые промпты
- `lib/LLM.php`: `LLM::ask()` / `LLM::askJson()`, JSON-парсинг с фолбэком,
  профили в `config.php` (`llm_profiles`, ключи из `.env`).
- Паттерн промптов с защитой от prompt injection (см. `checkFreeAnswer()`:
  оборачивание пользовательского текста в теги-разделители) — использовать
  такой же подход для анализа самопрезентации кандидата.
- Rate-limiting уже есть (`hitFreeAnswerRateLimit()` в `Controller.php`) —
  переиспользовать тот же подход для новых LLM-вызовов (анализ самопрезентации,
  финальный отчёт).

### 2.5. Мультиязычность и шаблоны
- Smarty, шаблоны по языкам `templates/{lang}/...` + общие строки в
  `translations/{lang}.php` (`{translate}` блок). Статические тексты компании
  и описание вакансии — обычные `.tpl` по языкам, как `challenge-mariadb.tpl`.

### 2.6. Платный доступ — переиспользовать почти нечего, проверено отдельно
Проверено специально: в проекте **нет** биллинг/подписочной инфраструктуры.
- `templates/*/donate.tpl` + виджет Lava.top — это статичная страница
  добровольных донатов (iframe/ссылки на Lava.top, Ko-fi, CloudTips,
  NOWPayments), без бэкенд-интеграции, без вебхука, без таблицы заказов.
- Таблица `donations` (`sql/schema.sql`) — вручную ведущийся леджер для паблик-
  отображения "недавних донатов", не источник истины для доступа к фичам.
- В `users` нет флага premium/подписки/срока действия. Единственный похожий по
  духу механизм — `users.hide_ad_till` (дата, судя по коду выставляется вручную)
  и паттерн его использования в `lib/User.php` (`(hide_ad_till is null or
  hide_ad_till < current_date) show_ad`) — это ближайший существующий пример
  "перка с датой истечения", на который можно ориентироваться при проектировании
  сущности доступа к интервью (см. п. 3.5), но сам по себе он для новой фичи не
  подходит (привязан к рекламе, не платный).
- Вывод: платный гейт (сущность "доступ куплен/действует" + сам приём оплаты)
  — это **новая** подсистема, не переиспользование существующей. Решение по
  тому, встраивать ли реальную оплату (например, через Lava.top API/вебхук) в
  рамках этой задачи или выдавать доступ вручную на первом этапе — см. п. 3.5
  и открытый вопрос №5.

### 2.7. Грейды и рекомендации
- `grades` / `grades_localization`, `Controller::test_grade()` с уже готовой
  картой уровней (`intern/junior/middle/senior`) — переиспользуем термины и,
  возможно, саму сущность "грейда" для итогового результата.
- `achievements` / `user_achievements` — можно на будущее добавить
  ачивку "прошёл собеседование на Х уровень", не обязательно для MVP.

### 2.8. Страница профиля — есть готовый паттерн списка прошлых попыток
Проверено отдельно (нужно для требования "все попытки интервью доступны из
профиля"): `Controller::user_profile()` (`lib/Controller.php:1483`) уже
собирает и показывает пользователю несколько историй — вопросы (`getQuestions()`),
тесты (`getTests()`), ачивки, — рендерит их в `templates/user_profile.tpl`
как клиентские таблицы Tabulator.js (весь список отдаётся одним JSON,
пагинация/сортировка на клиенте — единственный пагинационный паттерн, который
вообще есть в проекте). `User::getTests()` (`lib/User.php:1416`) — почти
готовый шаблон для нового `getInterviewSessions()`:
```php
SELECT tests.id, created_at::date, closed_at::date, ...,
       COUNT(tq.question_id) tasks_count, COUNT(tq.solved_at) tasks_solved_count,
       COALESCE(gl_lang.title, gl_en.title, '') grade
FROM tests JOIN test_questions tq ON ... WHERE tests.user_id = :user_id ...
```
**Важный нюанс, который нельзя слепо копировать**: у таблицы тестов в текущем
профиле клик по строке фактически не работает (`user_profile.tpl` использует
чужой `id` для перехода — обработчик `rowClick` навешен на `tasksTable`, а не
на `testsTable`, и ссылается на поля `category`/`slug`, которых у теста нет,
хотя маршрут `/{lang}/test/{id}/result` → `Controller::test_result()`
существует и рабочий). Для интервью **нужно сделать рабочий клик**, а не
повторить этот баг — план ниже (п. 3.8) явно на это указывает.

## 3. Что нужно разработать с нуля

### 3.1. Новые сущности / данные
1. **Позиции (должности)** — для старта реализации сужено до **2 позиций**:
   `sql_developer` и `data_analyst` (остальные из первоначального списка —
   Data Engineer, DBA, BI-аналитик — отложены на потом). Список пока
   захардкожен в PHP-конфиге (по аналогии с константами Controller), без
   отдельной таблицы. Если понадобится расширяемость через админку —
   отдельная таблица `interview_positions` + `interview_positions_localization`.
2. ✅ **Связь позиция → вопросы — сделано, реализовано проще, чем планировалось
   изначально**: вместо мапы "позиция → категории" с весами (как думали
   раньше) сделана прямая таблица `public.interview_questions(position,
   grade, question_id)` — каждая строка сразу говорит, что вопрос `question_id`
   уместен для `position` на грейде `grade` (2/3/4 = Junior/Middle/Senior,
   переиспользует `grades`, см. DDL-комментарий). Так проще: не нужно вводить
   веса категорий и решать, как из веса темы получить конкретный список
   вопросов — подбор пула вопросов для сессии превращается в прямой
   `SELECT question_id FROM interview_questions WHERE position = ? AND grade = ?`.
   Готовые артефакты:
   - **[sql/interview_questions_ddl.sql](sql/interview_questions_ddl.sql)** —
     DDL (PK по всем трём колонкам, FK на `questions`/`grades`, индекс под
     выборку по `(position, grade)`).
   - **[scripts/classify_interview_questions.py](scripts/classify_interview_questions.py)** —
     скрипт, который классифицирует экспорт вопросов (`questions.json`,
     `select ... from questions join questions_localization ...`) по
     позиции/грейду эвристикой (ключевые слова DDL/DML/индексы/PostGIS/
     MariaDB-трivia → `sql_developer`, остальное → обе позиции; грейд — по
     `rate` с тем же перекрытием окон, что и в п. 4.1: junior←rate 1-2,
     middle←rate 2-4, senior←rate 3-5).
   - **[sql/interview_questions_fill.sql](sql/interview_questions_fill.sql)** —
     результат прогона: из 451 экспортированных вопросов 436 попали в
     `sql_developer`, 378 — в `data_analyst` (378 пересекаются, 58 только у
     SQL Developer), 15 исключены целиком (бренд-тривия MariaDB Foundation +
     сценарии Data Engineering, вне текущих 2 позиций) — итого 1614 строк.
   - **Важная оговорка**: это эвристика по ключевым словам с точечными
     ручными правками, а не LLM-классификация — годится как рабочий старт,
     но не заменяет п. 3.7 (`interview_skill_tags` через LLM) на будущее,
     когда позиций/вопросов станет больше и точность важнее скорости
     bootstrap'а. Список сомнительных случаев — в отчёте, который печатает
     скрипт (`--report-out`).
   - `categories` при этом **не заменены и не тронуты** — они по-прежнему
     нужны отдельно, для разбивки "сильные/слабые темы" в финальном отчёте
     (п. 4.2), просто больше не участвуют в фильтрации вопросов по позиции.
3. ✅ **Профиль вымышленной компании — сделано, экран собран и проверен в
   браузере**. Отличие от изначального плана: не "1 компания на позицию", а
   **1 компания сразу на обе позиции** (у реальной компании и правда обычно
   несколько открытых вакансий одновременно) — это также означает, что
   "выбор должности и грейда" и "знакомство с компанией" **объединены в один
   экран** (шаг 2 флоу, п. 1), а не идут отдельными шагами: страница сама
   показывает самопрезентацию компании, обе вакансии с описанием, и грейды с
   требованиями — кандидат сразу видит и контекст, и выбор, без промежуточного
   шага выбора позиции вслепую.
   - Компания — **Meridian Logistics** (вымышленная логистическая компания:
     TMS/WMS, трекинг отправлений, перевозчики, склады — естественно
     объясняет, зачем компании и SQL Developer, и Data Analyst).
   - **[templates/interview-start.tpl](templates/interview-start.tpl)** —
     каркас страницы (по образцу `about.tpl`: `short-header.tpl` +
     `top-menu.tpl`/`m.top-menu.tpl` в зависимости от `$MobileView` +
     `footer.tpl`/`m.footer.tpl`), плюс собственный `<style>`-блок.
   - **[templates/en/interview-start.tpl](templates/en/interview-start.tpl)** /
     **[templates/ru/interview-start.tpl](templates/ru/interview-start.tpl)** —
     контент: хиро-блок (лого, тег-лайн, самопрезентация, цитата
     представителя компании), затем 2 карточки позиций, в каждой — 3
     карточки грейдов (Junior/Middle/Senior) с требованиями и своей кнопкой
     "Start Interview"/"Начать собеседование" (6 кнопок всего — по одной на
     пару позиция/грейд, а не один общий CTA).
   - **[images/interview/meridian-logistics-logo.svg](images/interview/meridian-logistics-logo.svg)**
     и **[images/interview/meridian-logistics-representative.svg](images/interview/meridian-logistics-representative.svg)** —
     логотип и иллюстрированный (не фотореалистичный — так безопаснее и
     соответствует стилю уже существующих SVG-иллюстраций уроков,
     `images/lessons/*.svg`) аватар представителя компании.
   - `Controller::interview_start()` (`lib/Controller.php`) + роут
     `interview-start` (`lib/Router.php`) — минимальная связка, чтобы страница
     реально открывалась (`/{lang}/interview-start`). **По дизайну эта страница
     публичная**: она не проверяет вход и не редиректит неавторизованных на
     логин. `findActiveSession()` (Этап 2, п. 3.2.1) вызывается здесь **только
     если пользователь уже залогинен** (чтобы показать приглашение продолжить
     начатую сессию вместо выбора позиции/грейда) — для анонимного посетителя
     этот вызов просто пропускается, и сразу показывается обычный экран выбора.
     Вход и оплата (`checkAccess`/`interview_entitlements`) на этот экран не
     завязаны вовсе — обе проверки происходят позже, в `interview_create`,
     сразу после выбора конкретной пары позиция/грейд (клик "Start Interview").
   - Проверено в браузере (без обращения к прод-БД — рендер собирался локально
     через Smarty напрямую): desktop и mobile, найден и исправлен реальный
     баг вёрстки (глобальный `main { display: grid; }` в `style.css`
     растягивал несколько верхнеуровневых секций по высоте вьюпорта —

   - **Открыто**: 6 кнопок "Start Interview" ведут на

### 3.2. Новая бизнес-логика
1. **`lib/Interview.php`** (по аналогии с `lib/Test.php`):
   - `findActiveSession(userId): ?array` — возвращает текущую незавершённую
     сессию пользователя, если она есть (статус `intro`/`intro_followup`/
     `in_progress`), иначе `null`. Читает тот же инвариант "не более одной
     активной сессии", который на уровне БД гарантирует партиальный уникальный
     индекс (п. 3.1.4) — вызывается на странице компании (`interview_start`,
     флоу п. 1, шаг 1), но **только если пользователь уже залогинен**
     (`interview_start` сам по себе публичный и не требует входа — см. п. 3.1.3);
     для анонимного посетителя вызов просто пропускается. Проверка входа как
     таковая (авторизован ли пользователь вообще) на этом экране **не**
     выполняется и не редиректит на логин — это сознательно отложено до клика
     "Start Interview" (см. `checkAccess` ниже и флоу, шаг 2).
   - `checkAccess(userId, position, grade)` — проверяет то, что зависит от
     выбранной пары — есть действующее право доступа (оплата, п. 3.5) и не
     нарушен кулдаун повторной попытки именно для этой позиции/грейда (п. 4.4).
     Сама проверка входа (авторизован ли пользователь) выполняется **перед**
     вызовом `checkAccess()`, в `interview_create`: если пользователь не
     залогинен — редирект/попап логина с сохранением выбранной пары позиция/
     грейд, чтобы после успешного входа или регистрации сразу продолжить с
     `checkAccess()` и `create()`. И вход, и `checkAccess()` вызываются **в
     момент нажатия "Start Interview"** — то есть в `interview_create`,
     непосредственно перед `create()` (флоу п. 1, между шагами 2 и 3) — раньше
     нельзя: оплата привязана к попытке в целом, а не к конкретной паре, но
     самого выбора пары ещё нет на шаге 1, а кулдаун вообще специфичен для пары
     и не может быть проверен раньше, чем она выбрана.
   - `create(position, grade, userId)` — создаёт `interview_sessions`, подбирает
     стартовый пул вопросов (категории по позиции, сложность по грейду через
     `questions.rate`), **исключая вопросы из предыдущих сессий того же
     пользователя по той же паре позиция/грейд** (п. 4.4), сохраняет в
     `interview_session_questions`.
   - `saveSelfIntro(sessionId, text)` — сохраняет текст, вызывает LLM-анализ
     (включая оценку соответствия позиции/грейду, п. 4.5). Если LLM вернул
     `followup_question` — переводит сессию в статус `intro_followup` и
     возвращает вопрос для показа кандидату, **не создавая** ещё пул вопросов
     интервью; иначе сразу переходит к `create()`. При необходимости
     корректирует целевую сложность пула (например, если кандидат явно
     слабее заявленного грейда — подмешать более простые вопросы), но никогда
     не отказывает в продолжении из-за несоответствия (п. 1).
   - `saveIntroFollowupAnswer(sessionId, answer)` — сохраняет ответ на
     уточняющий вопрос в `self_intro_analysis.followup.answer` (без
     дополнительного LLM-вызова на этом шаге — ответ используется позже, в
     финальном отчёте, п. 4.5), переводит статус в `in_progress` и вызывает
     `create()`.
   - `getNextQuestion(sessionId)` — отдаёт следующий вопрос; здесь же простая
     адаптивная логика (см. п. 4.1).
   - `saveAnswer(sessionId, questionId, answer)` — прогоняет через существующие
     `Question::checkQuery*()` / `checkAnswers()` / `checkFreeAnswer()`; если
     ответ неверный — дополнительно вызывает LLM-оценку "близости" к решению и
     либо генерирует подсказку с правом на повторную попытку, либо короткий
     комментарий с переходом дальше (полная логика — п. 4.3); пишет результат
     (включая `llm_closeness`/`llm_feedback`/`attempt_number`) в
     `interview_session_questions`.
   - `finish(sessionId)` — считает финальный результат (см. п. 4.2), делает один
     финальный LLM-вызов для качественной обратной связи и рекомендаций
     (бюджет на LLM выше, чем у бесплатных фич — см. п. 1), сохраняет `result`
     и `final_score`.
2. **`Controller`**: новые экшены (по образцу `challenge_mariadb_*`).
   `interview_start` — **единственный публичный** из этого списка, доступен
   без входа: если пользователь залогинен, вызывает `findActiveSession()` —
   если активная сессия есть, показывает текст + кнопку "Продолжить интервью"
   вместо выбора позиции/грейда; если сессии нет (или пользователь не
   залогинен) — обычная страница компании с выбором позиции/грейда (п. 3.1.3).
   Все остальные экшены требуют входа (редирект на логин, если нет):
   `interview_create` (**здесь**, а не в `interview_start`, сначала проверяется
   вход — не авторизован → редирект на логин/регистрацию с сохранением
   выбранных `position`/`grade`, чтобы вернуться сюда же после входа, — затем
   `checkAccess(userId, position, grade)` — оплата + кулдаун для выбранной
   пары; любой отказ → сообщение о недоступности/пейволл/логин, не создание
   сессии), `interview_intro` (компания + форма самопрезентации),
   `interview_intro_followup` (показ LLM-сгенерированного уточняющего вопроса
   и приём ответа на него — рендерится только когда `status = 'intro_followup'`;
   если LLM не запросил уточнение, этот шаг просто пропускается),
   `interview_question` (показ текущего вопроса + сабмит ответа, включая
   повторную попытку при `close`-вердикте), `interview_result` (итоговый отчёт).
3. **`Router.php`**: роуты `interview`, `interview-start`, `interview-intro-followup`,
   `interview-question`, `interview-result` (аналогично `challenge-mariadb-*`).
4. **Промпты для LLM** (новые, но через существующий `LLM::askJson()`):
   - анализ самопрезентации кандидата, **включая соответствие выбранной
     позиции/грейду** (п. 4.5) → JSON `{claimed_experience, seniority_signal,
     focus_topics: [...], flags: [...], fit: {matches: bool, concerns:
     [...]}, followup_question: string|null}`;
   - **оценка неверного ответа "близко/далеко от решения" + комментарий**
     (новое, ключевое для "живого" ощущения интервью, см. п. 4.3) → JSON
     `{closeness: "close"|"far", comment: string, hint: string|null}`. Вход —
     текст задачи, эталонное решение (`solution_query` / `is_valid`-ответы),
     ответ кандидата и — для `query` — диагностика из
     `Question::checkQueryResult()` (не выполнился / неверные строки / неверные
     колонки), это подсказывает LLM, где именно ошибка;
   - генерация финального отчёта — качественный текст поверх количественных
     метрик (обязательный шаг, не опционально, раз фича платная — см. п. 4.2).
5. **Рекомендации по темам**: сопоставление слабых `categories` с материалами
   `/lessons`. Уточнено: уроки сейчас **не размечены** по темам/категориям так же,
   как вопросы. Ручная мапа не нужна — вместо неё строится автоматический скрипт
   разметки (см. п. 3.6, обязательный для MVP, не опциональный).

### 3.5. Платный доступ (новая подсистема — см. п. 2.6, готового нет ничего)
✅ **Вариант A реализован**: таблица `interview_entitlements`
(`user_id`, `granted_at`, `expires_at null`, `sessions_total`,
`sessions_used`, `source varchar` — `manual`/`lava`/`promo`) смигрирована
(`sql/interview_entitlements_ddl.sql`, см. Этап 1). Доступ выдаётся вручную
администратором после оплаты вне системы (перевод, тот же Lava.top как
способ приёма денег, но без API-интеграции). Страница `interview_payment`
(п. 3.2.2/3.3) показывает ссылку из `config.php` (`interview.lava_payment_url`,
читается из `.env` `INTERVIEW_LAVA_PAYMENT_URL`) — тот же паттерн статичной
ссылки, что уже используется в `donate.tpl`. `Interview::hasPaidAccess()` проверяет
наличие активной записи с `sessions_used < sessions_total`; `Interview::create()`
атомарно списывает одну сессию (`sessions_used + 1` с `FOR UPDATE`) в той же
транзакции, что и создание сессии — исправлен баг, из-за которого счётчик
изначально не инкрементировался при создании сессии.
- **Вариант B (интеграция с Lava.top API) — спроектирован, к реализации**.
  Документация API Lava.top: https://developers.lava.top/ru (OpenAPI-спецификация:
  https://gate.lava.top/docs/documentation.yaml). Решение: **одна таблица** —
  расширяем `interview_entitlements`, отдельную таблицу платежей не заводим
  (продаём только пакеты сессий, одна оплата = одна запись доступа; подписки не
  планируются — если появятся, платежи выносим в отдельную таблицу).

  **Что даёт API (проверено по спецификации):**
  - База `https://gate.lava.top`, авторизация заголовком `X-Api-Key` (ключ —
    `app.lava.top/integrations/public-api`), лимит 50 req/s с IP.
  - `POST /api/v3/invoice` — создание контракта: `email`, `offerId`, `currency`
    (RUB/USD/EUR), опционально `buyerLanguage` (EN/RU/ES), `promoCode`,
    `clientUtm`, `successful_return_url`/`failure_return_url`/`cancel_return_url`.
    Ответ: `id` (contractId), `status`, `paymentUrl` — на него редиректим.
  - `GET /api/v2/invoices/{id}` — статус контракта (`NEW`/`IN_PROGRESS`/
    `COMPLETED`/`FAILED`), сумма, покупатель.
  - `GET /api/v2/products` — получить `offerId` (продукт и цена заводятся в UI
    Lava.top).
  - Вебхуки: `payment.success`, `payment.failed`, `refund.success`,
    `chargeback.initiated` (+ события подписок — не используем). При ответе
    4xx/5xx — до 19 повторов в течение ~5 часов.

  **Ограничения, влияющие на дизайн:**
  - Вебхуки **не подписываются** (нет HMAC) — только общий секрет (Basic auth
    или `X-Api-Key`, задаётся в кабинете). Поэтому каждый `payment.success`
    перепроверяем запросом `GET /api/v2/invoices/{contractId}`.
  - Нет поля для своих метаданных (user_id) — связь "платёж ↔ пользователь"
    только через `contractId`, сохранённый при создании счёта.
  - Вебхуки `refund.success`/`chargeback.initiated` имеют другой формат
    (`event_type`, `data.*`) и **не содержат документированного `contractId`**
    (есть `refund_id`, `customer_email`, `product_id`); в примере спецификации
    `refund_id` совпадает с `contractId` платежа — уточнить у поддержки
    (`@lava_sup_bot`) до реализации (открытый вопрос №5).
  - Нет песочницы — тестирование на реальном дешёвом продукте / промокоде 100%
    + ручная отправка сохранённых payload на вебхук.
  - Параметры возврата (`?invoiceId=…&status=success`) подделываются — только
    для UI, доступ по ним не выдаётся.

  ✅ **Схема (миграция `sql/interview_entitlements_lava.sql`) — применена в БД**;
  `sql/interview_entitlements_ddl.sql` обновлён до итогового состояния:
  ```sql
  ALTER TABLE interview_entitlements
      ADD COLUMN status varchar(16) NOT NULL DEFAULT 'active'
          CHECK (status IN ('pending','active','failed','refunded')),
      ADD COLUMN lava_contract_id uuid UNIQUE,   -- NULL для manual/promo
      ADD COLUMN lava_offer_id uuid,
      ADD COLUMN amount numeric(12,2),
      ADD COLUMN currency varchar(3),
      ADD COLUMN paid_at timestamp,
      ADD COLUMN raw_webhook jsonb;
  GRANT INSERT, UPDATE ON interview_entitlements TO sqltester;
  GRANT USAGE ON SEQUENCE interview_entitlements_id_seq TO sqltester;
  ```
  Default `'active'` оставляет существующие manual/promo-записи рабочими.

  **Изменения в коде:**
  - `Interview::hasPaidAccess()` и списание сессии в `Interview::create()` —
    добавить `AND status = 'active'` (иначе доступ появится в момент чекаута).
  - `.env`: `LAVA_API_KEY`, `LAVA_WEBHOOK_SECRET` (секреты
    только в `.env`); `config.php` читает их в `interview.lava_api_key` /
    `interview.lava_webhook_secret` — по образцу существующего
    `interview.lava_payment_url`.
  - `config.php`, `interview.packages`: мапа пакетов `offerId → sessions_total`
    — единственное место, где задаются пакеты. Валюта и цена — **по языку
    сайта** (`interview.pricing[lang]` → `currency`, `price` для отображения),
    напр. `ru` → RUB, `en`/`pt`/`fr`/`es` → USD/EUR. Эта же `currency`
    передаётся в `POST /api/v3/invoice` (цена в Lava.top задаётся на оффере во
    всех нужных валютах; `amount` из ответа сохраняется в запись).
  - Новый `lib/LavaClient.php`: `createInvoice()`, `getInvoice()` (curl,
    `X-Api-Key`, таймауты, логирование ошибок).

  **Поток:**
  1. Чекаут (`interview_payment` → action `interview-checkout`, только для
     залогиненного): email берётся из `users.email` (`User::getEmail()`); если
     его нет (OAuth-пользователь) — поле email на странице оплаты, введённое
     значение **сохраняется в профиль** через `User::setEmail()` (валидация и
     проверка уникальности уже там; при `email_taken` — показать ошибку, чекаут
     не создавать). Затем `POST /api/v3/invoice` с этим email, `currency` из
     `interview.pricing[lang]` и `buyerLanguage` по языку сайта (Lava.top
     поддерживает только EN/RU/ES: `pt`/`fr` → EN) →
     `INSERT interview_entitlements (user_id, source='lava', status='pending',
     sessions_total=<из мапы>, lava_contract_id, lava_offer_id, amount,
     currency)` → редирект на `paymentUrl`.
  2. Вебхук `POST /lava/webhook`:
     - проверить секрет через `hash_equals()`, иначе 401;
     - найти запись по `contractId`; неизвестный контракт → 200 и игнор (в лог);
     - `payment.success` → `GET /api/v2/invoices/{contractId}`, убедиться в
       `COMPLETED` и совпадении суммы/валюты → `UPDATE ... SET status='active',
       paid_at=now(), raw_webhook=:payload WHERE lava_contract_id=:cid AND
       status='pending'` (идемпотентно: повтор вебхука меняет 0 строк);
     - `payment.failed` → `status='failed'` (только из `pending`);
     - `refund.success`/`chargeback.initiated` → `status='refunded'`,
       `expires_at=now()` (не удаляем — использованные сессии остаются
       консистентными);
     - ошибка БД/API → 5xx, чтобы Lava.top повторила доставку; иначе 200.
  3. Возврат пользователя на `successful_return_url` → страница читает статус
     записи: `active` — "доступ открыт", `pending` — "ждём подтверждения
     оплаты" (автообновление), `failed` — предложение повторить.
  - Брошенные чекауты (`pending` старше суток) — периодически переводить в
    `failed` (cron-скрипт) либо удалять.
  - Вариант A (ручная выдача, `source='manual'`) остаётся как запасной путь —
    ручные возвраты и сбои интеграции.
  - Оценка: ~2–3 дня (миграция, `LavaClient`, чекаут, вебхук, страница
    статуса, ручное тестирование на реальном продукте).
- В обоих вариантах именно `interview_entitlements` (а не прямая проверка
  оплаты) — источник истины для `Interview::hasPaidAccess()`, чтобы вариант
  A→B можно было заменить, не трогая остальную логику фичи.

Уточнено: уроки в `/lessons` сейчас **не размечены** темами/категориями так же,

### 3.9. Опционально (фаза 2+): RAG-подход к рекомендациям уроков через векторный поиск
Обсуждалась альтернатива п. 3.6 (категорийная разметка уроков): вместо
привязки урока к фиксированному списку `categories`, у каждого урока
считается embedding-вектор его содержимого, а рекомендации на финальном
экране интервью (п. 4.2) ищутся векторным similarity-поиском — запросом
может быть прямо текст "слабых мест" кандидата из финального LLM-отчёта, а
не название категории.

**Решение**: для MVP используем простой категорийный матчинг (п. 3.6) — при
текущем объёме контента (`/lessons`, порядка нескольких десятков уникальных
уроков) он закрывает задачу почти бесплатно, переиспользуя тот же
таксономический механизм, что уже даёт разбивку "сильные/слабые темы" в
самом отчёте (п. 4.2). RAG даёт более гибкий семантический матчинг (можно
искать не только по фиксированным темам, но и по нюансам формулировки
слабых мест) и лучше масштабируется при росте базы уроков — но ценой новой
инфраструктуры: расширение БД под векторы (в проекте сейчас не используется
— ни pgvector, ни какая-либо embedding-инфраструктура), пайплайн генерации
эмбеддингов (ещё один LLM/embedding-вызов на урок + переэмбеддинг при правке
контента), и меньшая прозрачность рекомендаций (числовая похожесть вместо
явного тега темы, сложнее объяснить/отладить, почему порекомендован именно
этот урок).

Если появится сигнал, что категорийного подхода не хватает (уроков станет
много и они не будут укладываться в существующую таксономию `categories`,
или качество рекомендаций из п. 3.6 окажется низким на практике) — заменить
`lesson_categories` (п. 3.6) на:
- расширение `lessons`/`lessons_localization` embedding-колонкой (`vector`,
  через расширение `pgvector` для PostgreSQL);
- разовый/периодический скрипт (по аналогии с `scripts/tag_lessons_categories.php`
  из п. 3.6, но зовущий embedding-API вместо `askJson()`) для пересчёта
  векторов при добавлении/правке уроков;
- в `Interview::finish()` — вместо `SELECT ... FROM lesson_categories WHERE
  category_id = ANY(weak_categories)` — векторный `ORDER BY embedding <=>
  query_embedding LIMIT N` по эмбеддингу текста слабых мест кандидата.

Это не блокирует MVP и не входит в его объём — зафиксировано здесь как
осознанно отложенное решение, а не забытая идея.

## 4. Ключевые алгоритмы

### 4.1. Адаптивный подбор вопросов (MVP — правило-ориентированный, без LLM)
- **Стартовый набор — фиксировано 5 вопросов**: 2 теоретических (`answer` /
  `free_answer` по темам позиции), 2 практических SQL (`query`), 1
  "профессиональные навыки" (`free_answer`, про опыт/подход к работе, слабо
  привязан к конкретной SQL-теме — см. этап 0, п. 4 плана про необходимость
  такого контента в банке). И тема/позиция, и сложность отбираются **одним
  запросом** к `interview_questions` (п. 3.1.2): `WHERE position = ? AND
  grade = ?` — вопрос уже находится в нужном грейд-окне (junior←rate 1–2,
  middle←rate 2–4, senior←rate 3–5), т.к. именно так таблица заполнена;
  внутри выборки вопрос типа `query`/`answer` берётся случайно, тема как
  таковая (`categories`) на этом этапе не участвует — она нужна отдельно,
  только для разбивки по темам в финальном отчёте (п. 4.2).
- **Набор расширяется по ходу интервью** (а не фиксирован на 5) — по итогам
  ответов может добавляться до нескольких дополнительных вопросов той же
  пропорции теория/практика, аналогично стартовой логике ниже. Верхняя
  граница длины интервью определяется не количеством вопросов напрямую, а
  бюджетом LLM-вызовов на сессию (10–20, конфигурируется — п. 4.3): когда
  бюджет подходит к концу, набор перестаёт расти и сессия идёт к завершению.
- После каждого ответа:
  - 2 ошибки подряд в теме → следующий вопрос по этой теме на ступень проще (или
    тема временно исключается);
  - 2 верных ответа подряд в теме на грейд-уровне → один вопрос усложняется;
  - если самопрезентация (`seniority_signal`, п. 4.5) явно указывает на другой
    уровень — сдвигается целевой `rate` для всего оставшегося набора.
- LLM здесь **не обязателен** — простая арифметика поверх `rate`/`interview_questions`.
  LLM-подбор "живых" уточняющих вопросов — кандидат для фазы 2, не для MVP
  (сложнее контролировать качество и стоимость).

### 4.2. Итоговый скоринг
- Базовый процент = взвешенная доля решённых/верно отвеченных вопросов
  (вес выше для более сложных/старших по грейду вопросов), аналогично духу
  `Test::calculateResult()`, но в виде процента, а не ступенчатого грейда.
- Разбивка по темам: % успеха на каждую `category`, встретившуюся в сессии →
  это и есть "сильные/слабые стороны".
- Рекомендации: темы с % ниже порога (например, < 60%) → ссылки на
  соответствующие уроки/материалы.
- Итоговый качественный комментарий — один финальный вызов LLM с агрегированными
  данными (темы, баллы, самопрезентация) → человекочитаемый отчёт-фидбек в духе
  "сильные стороны: ..., стоит подтянуть: ..." (обязателен, не опционален —
  раз фича платная, качественный фидбек и есть часть продукта).

### 4.3. Комментарий LLM на неверный ответ + повторная попытка ("живое" интервью)
Ядро того, что отличает эту фичу от обычного теста с чекмарками. Срабатывает
на **любой** тип вопроса (`query`/`answer`/`free_answer`), как только
объективная проверка (`checkQuery*`/`checkAnswers`/`checkFreeAnswer`) признала
ответ неверным:

1. Собрать контекст для LLM: текст задачи, эталон (`solution_query` или
   `is_valid`-ответы), ответ кандидата, и — для `query` — диагностику
   несовпадения от `checkQueryResult()` (запрос не выполнился / другое число
   строк/колонок / данные не совпадают), для `free_answer` — уже посчитанный
   `score` из `checkFreeAnswer()`.
2. Один вызов `LLM::askJson()` → `{closeness, comment, hint}`:
   - **`close`** (ответ по сути на правильном пути, но с конкретной
     поправимой ошибкой — опечатка в имени колонки, неверный тип JOIN,
     упущенный `GROUP BY`, близкий, но не точный порог score у `free_answer`):
     кандидату показывается `hint` (наводящая подсказка, **без** прямого
     ответа) и даётся повторная попытка на тот же вопрос
     (`attempt_number += 1`, до `max_attempts`, по умолчанию 2).
   - **`far`** (принципиально не туда, синтаксическая каша, "не знаю"):
     показывается короткий поясняющий `comment` (что означало правильное
     решение, на пальцах, тоже без сценария "просто дать ответ на будущее")
     и сессия переходит к следующему вопросу без повторной попытки.
   - Порог между `close`/`far` — задача классификации, отдаётся на откуп
     промпту/модели, а не жёстким числовым правилам (в отличие от адаптивности
     по темам в п. 4.1, которая как раз рулбейз).
3. Оба случая пишутся в `interview_session_questions.llm_closeness`/
   `llm_feedback`, и участвуют в стенограмме результата (п. 3.1.5).
4. Ограничение стоимости: это ровно один дополнительный LLM-вызов на каждый
   **неверный** ответ (не на каждый ответ) — приемлемо в платном сценарии
   (см. п. 1). Уточнённый бюджет: **10–20 вызовов LLM за сессию**, из них
   фиксированные 2 (анализ самопрезентации + финальный отчёт), обязательные
   по числу вопросов типа `free_answer` (оценка `checkFreeAnswer`, уже так
   работает вне зависимости от этой фичи), и по одному на каждый неверный
   ответ/повторную попытку. Лимит **настраивается в `config.php`** (новый
   параметр, например `interview_llm_call_budget`, по умолчанию в диапазоне
   10–20) — при приближении к лимиту `Interview` перестаёт добавлять новые
   вопросы (см. п. 4.1) и переходит к завершению сессии, вместо жёсткого
   обрыва на середине вопроса. `checkAccess`/rate-limiting всё равно нужны
   против abuse (переиспользовать паттерн `hitFreeAnswerRateLimit()`).
5. Тон формулировок `comment`/`hint` в промпте должен быть выдержан как речь
   живого интервьюера (нейтрально-доброжелательный технический лид), а не как
   отчёт автотестера — это и есть требование "приблизить симуляцию к
   реальному собеседованию".

### 4.4. Повторная попытка на следующий день и уникальность вопросов
- **Кулдаун**: `Interview::checkAccess()` не позволяет создать новую сессию
  для той же пары (`user_id`, `position`, `grade`) в тот же календарный день,
  что и последняя сессия этого пользователя по этой паре — повторная попытка
  доступна начиная со следующего календарного дня (сравнение `date`, а не
  разница в 24 часа). Достаточно `SELECT max(created_at) ... WHERE status =
  'finished'` по индексу из п. 3.1.4 — новой сущности не требуется.
- **Отсутствие повторов вопросов**: при `Interview::create()` для новой
  попытки собирается множество `question_id` из **последних 3 попыток**
  этого пользователя по той же паре позиция/грейд, и эти вопросы исключаются
  из выборки для новой сессии. Поскольку между попытками действует суточный
  кулдаун, "последние 3 попытки" на практике примерно соответствуют и
  "последним ~3 дням" — оба ограничения (по числу и по давности), заданные
  изначально, здесь совпадают, отдельного выбора между ними не требуется.
- **Фолбэк на исчерпание пула**: если после исключения использованных
  вопросов в нужной категории/сложности вопросов не хватает — сначала
  ослабляется точность подбора (соседняя сложность/категория), и только если
  совсем не хватает — допускается повтор наименее давно виденных вопросов
  (лучше повтор с фидбеком, чем сорванная сессия). Порог "не хватает"
  зависит от реального размера банка вопросов на позицию/грейд (см. этап 0,
  п. 3 плана — нужно свериться при подготовке).

### 4.5. Анализ соответствия самопрезентации позиции/грейду + уточняющий вопрос
Цель — мягко проверить, насколько заявленный в самопрезентации опыт
согласуется с выбранными кандидатом позицией и грейдом, и при необходимости
получить дополнительный сигнал одним уточняющим вопросом — но **никогда** не
блокировать прохождение интервью из-за несоответствия (см. п. 1).

1. `Interview::saveSelfIntro()` вызывает `LLM::askJson()` с контекстом: текст
   самопрезентации, выбранные позиция и грейд, краткое описание ожиданий от
   этого грейда (переиспользовать формулировки `grades`/`grades_localization`,
   п. 2.7, и/или требования вакансии из шаблона компании, п. 3.1.3) → на выходе
   `fit.matches` (bool) и `fit.concerns` (список конкретных нестыковок, если
   есть), плюс уже существующие `claimed_experience`/`seniority_signal`/
   `focus_topics`.
2. **Уточняющий вопрос — не отдельный вызов**, а часть того же ответа LLM:
   если модель считает нужным прояснить конкретный момент (например,
   кандидат заявил "middle", но не упомянул ничего про оптимизацию
   запросов/индексы), она возвращает `followup_question` — один точечный
   вопрос по конкретной нестыковке, а не общий "расскажите про себя ещё раз".
   Если `fit.matches = true` или расхождения незначительны — `followup_question
   = null` и интервью сразу переходит к `create()` (п. 3.2.1) без
   дополнительного экрана.
3. Если `followup_question` есть — статус сессии становится `intro_followup`,
   кандидату показывается `interview-intro-followup.tpl` (п. 3.3) с этим
   вопросом. Ответ сохраняется как есть, **без** повторного LLM-вызова на этом
   шаге (`saveIntroFollowupAnswer()`, п. 3.2.1) — это экономит бюджет LLM
   (п. 4.3: механизм остаётся в рамках уже заложенных 2 фиксированных вызовов
   на самопрезентацию/финал, а не добавляет третий).
4. Ограничение на MVP: **не более одного** раунда уточнения за сессию (без
   зацикливания "уточнение на уточнение") — если после ответа кандидата
   несоответствие всё ещё есть, это просто фиксируется в
   `self_intro_analysis` и переносится в финальный отчёт, а не порождает
   второй уточняющий вопрос. Более сложный многораундовый диалог — кандидат
   на будущее расширение, не для MVP.
5. **Что происходит с результатом анализа** (`fit.concerns`,
   `followup.question/answer`) — используется в двух местах, но нигде не
   останавливает интервью:
   - опционально, сразу после сохранения самопрезентации — короткая
     доброжелательная реплика от лица интервьюера (например: "у тебя, похоже,
     меньше опыта с продакшн-инцидентами, чем обычно ожидают на этом уровне —
     ничего страшного, продолжаем!"), не блокирующая переход к вопросам;
   - обязательно — как входные данные для финального LLM-отчёта
     (`Interview::finish()`, п. 4.2/3.2.1): концерны из самопрезентации
     превращаются в доброжелательные рекомендации ("на собеседованиях такого
     уровня также спрашивают про X — стоит подтянуть"), наравне с
     рекомендациями по темам вопросов.
   - на подбор сложности пула вопросов это уже влияет и без уточняющего
     вопроса — через `seniority_signal`, как было заложено в исходной версии
     плана (п. 4.1); уточняющий вопрос уточняет именно качество этого
     сигнала, а не заменяет его.
